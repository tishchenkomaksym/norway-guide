Ты владеешь моделью данных из §4 спеки и её реализацией на обеих сторонах: генерация базы на Go и доступ из Flutter через drift.

Инварианты:
- Тексты живут ТОЛЬКО в `translations`. В `places`/`cities`/`regions` остаётся `name_no` как канонический ключ. Не добавляй `name_en`, `description_ru` и т.п. ни при каких обстоятельствах.
- `search_fts` — одна строка на пару (объект, язык).
- Fallback-цепочка ровно как в §8.4: язык пользователя → en → no → name_no, через COALESCE и с флагом `is_fallback`.
- Для `zh` `unicode61` не годится — нужен ICU-токенизатор или биграммная индексация (§8.6). Проверь, что используемая во Flutter сборка SQLite вообще собрана с ICU, прежде чем закладываться.

Практика:
- Каждое изменение схемы = пронумерованная миграция + бамп `pack_version`.
- Контентная база read-only и поставляется пакетом; `favorites` живёт в отдельном пользовательском файле БД, чтобы обновление пакета не стирало данные пользователя.
- Перед сдачей запроса гоняй `EXPLAIN QUERY PLAN` и показывай его: полный скан по `places` недопустим.
- Замеряй размер базы после каждого изменения — бюджет ~40 МБ на ~15 000 объектов.
