# Пайплайн подготовки данных

Go-часть проекта: превращает открытые источники в `content.sqlite` и пакеты
регионов. Приложение — только витрина; вся тяжёлая работа здесь.

Состояние: написаны `cmd/probe` ([[probe-result]]), `cmd/extract`
([[measurements#Связь OSM с Wikidata]]) и `cmd/enrich`
([[measurements#Обогащение текстами]]). Дальше — `media`.

## Этапы

```
extract → toplist → enrich → media → gallery → optimize → build
```

| Команда | Что делает | Агент |
|---|---|---|
| `cmd/extract` | OSM `.pbf` → сырые POI, категории, `importance` | `osm-pipeline` |
| `cmd/toplist` | Дописывает места топ-20, которых нет в OSM | `osm-pipeline` |
| `cmd/enrich` | Wikidata, тексты Wikipedia и Wikivoyage | `wiki-enricher` |
| `cmd/media` | Главное фото (P18) с Commons, фильтр лицензий | `wiki-enricher` |
| `cmd/gallery` | Дополнительные фото из категории Commons (P373) | `wiki-enricher` |
| `cmd/optimize` | Пережатие снимков под бюджет бандла | `wiki-enricher` |
| `cmd/rules` | Коммуна и контакты для правил рыбалки и охоты | не назначен |
| `cmd/translate` | Наполнение `translations`, машинный перевод | `l10n-content` |
| `cmd/build` | Сборка SQLite, FTS5, пакеты | `sqlite-schema` |
| `cmd/preview` | Статичные превью карты для топ-1000 | не назначен |

`cmd/preview` появился из [[decisions#Карта вне MVP]] и в §3 спеки отсутствует.

## toplist

Курируемый список самых посещаемых мест — `internal/toplist`. Задан руками,
и это осознанно: `importance` считается по полноте разметки и отвечает на
вопрос «насколько объект известен», а не «куда едут люди». Тролльтунга
размечена одной точкой и по формальной шкале проигрывает районной церкви.

Вторая причина — извлечение из OSM не видит часть главных мест. Проверка
2026-09-10: из 25 кандидатов **9 отсутствовали** в `places-norway.jsonl`,
потому что парк скульптур, трамплин, горная дорога, железная дорога и
архипелаг не попадают ни в одну из наших категорий. `cmd/toplist` дописывает
их в `data/places-curated.jsonl` с координатами из Wikidata, дальше их
обогащают обычные `enrich` и `media`.

Сопоставление идёт по идентификатору Wikidata, а не по названию: в OSM одно
место подписано по-разному, и «Vøringsfossen» против «Vøringfossen» дали бы
две записи вместо одной.

Числа посещаемости хранятся только вместе с годом и ссылкой на источник,
а где надёжного числа нет — там ноль, и приложение цифру не показывает.
Единой официальной статистики по достопримечательностям в Норвегии нет:
SSB считает ночёвки и поездки, а не входы в конкретные места.

## gallery

`media` берёт свойство P18 — одно главное изображение на объект. Для карточки
этого мало, поэтому `gallery` добирает снимки из категории Commons (P373).
Применяется не ко всему каталогу, а к топ-20 и объектам выше порога
значимости: кадры в категориях разного качества.

## optimize

Замер 2026-09-10: 1 977 снимков с Commons при ширине 640 px весили **306 МБ**
— впятеро больше бюджета бандла. `optimize` уменьшает до 480 px и пережимает
JPEG. Спека просит WebP, и он был бы примерно на треть легче, но кодировщик
WebP в Go требует C-библиотеки; переход — отдельная задача вместе с `cwebp`
в тулчейне.

## extract

Потоковое чтение `norway-latest.osm.pbf` через `paulmach/osm` — файл 1.3 ГБ,
целиком в память не грузится.

Требования:
- Маппинг тегов в категории — **одной явной таблицей**, не разбросанными `if`.
- Для way и relation считать центроид, а не первый узел.
- Идентификаторы строго `osm:node/123` / `osm:way/…` / `osm:relation/…`.
- Промежуточный вывод в JSONL с сырыми тегами: переобработка не должна
  требовать повторного чтения `.pbf`.
- Прогон идемпотентный и перезапускаемый с середины.

Отчёт обязателен: количество по категориям и **доля объектов с тегом
`wikidata`** — см. [[#Риски]].

## enrich

Источники разделены по результатам замера ([[probe-result]]):

- **Города → Wikivoyage** (100% покрытия, формат путеводителя)
- **Места → Wikipedia** (90% против 40% у Wikivoyage)
- **Для `no` — только Wikipedia**, норвежского Wikivoyage не существует

Парсеры разные: структура статей не совпадает.

`summary` должен быть самостоятельным текстом на 2–3 предложения, а не
обрезанным началом статьи — офлайн это единственное, что увидит человек
([[data-model#translations]]).

Технически: общий HTTP-клиент с лимитером ~2 rps и дисковым кэшем, ретраи
с учётом `Retry-After`. Сбой запроса **никогда** не трактуется как «статьи нет».

Порядок работы: сначала Wikidata батчами по 50 идентификаторов — она даёт
названия статей по языкам, угадать которые нельзя (норвежская статья про
Bryggen называется «Bryggen i Bergen»). Затем тексты из Wikipedia
и Wikivoyage по этим названиям.

Кэш безусловный и без срока: чтобы обновить данные, каталог `data/cache`
удаляется целиком. Прогон по всей Норвегии — десятки тысяч запросов,
и правка парсера не должна стоить полного перекачивания.

`summary` чистится от фонетических вставок: английская Wikipedia начинает
статьи с транскрипции, и в коротком описании она занимает половину места
([[measurements#Качество текстов]]).

## media

Лицензии проверяются **до** скачивания: только CC0, CC BY, CC BY-SA.
NonCommercial, ND и fair use отбрасываются в лог. Поля `author`, `license`,
`source_url` обязательны.

Отчёт: сколько скачано, сколько отброшено и почему.

## build

Сборка `content.sqlite`, наполнение `search_fts`, `VACUUM`, `ANALYZE`,
замер фактического размера против бюджета ~40 МБ.
Результат: [[measurements#Сборка базы]].

**Схема живёт в `internal/packer/schema.go` и обязана совпадать со схемой
drift** в `app/lib/data/tables.dart`. Расхождение проявится не при сборке,
а при первом запросе на устройстве — то есть поздно и не у нас. Владелец
схемы — агент `sqlite-schema`.

Места привязываются к ближайшему городу в радиусе 25 км. Радиус намеренно
щедрый: норвежские достопримечательности часто лежат далеко за
административной границей, но воспринимаются как часть города.

Города отсекаются по значимости: из 53 найденных в районе Бергена в базу
попали 17. Хутора и мелкие деревни только засоряют список — их сотни,
а смотреть там нечего.

Биграммы для китайского в индексе пока не реализованы: языки `es`, `ru`, `zh`
появятся на этапе `translate`.

Затем обязательный прогон `license-auditor` с числами.

## Риски

**Матчинг OSM ↔ Wikidata — проверен 2026-09-10, риск снят.**

Опасение было: если тег `wikidata=Qxxx` проставлен у малой доли норвежских
POI, большинство мест останется без описаний. Замер по району Бергена
([[measurements#Связь OSM с Wikidata]]) показал 9% по всей выборке,
но **100% в топ-50 по значимости** и 99% в топ-100.

Тег и значимость коррелируют почти идеально: о безымянном заливе статью
не пишут. Поэтому обогащаем топ-N по `importance`, а не все POI. Нечёткий
матчинг по имени и координатам, который закладывался как запасной план,
**не нужен** — он работал бы там, где контента нет и в самой Wikipedia.

Практический порог: имеет смысл обогащать примерно до `importance >= 60`;
ниже доля связей быстро падает, а ценность объектов для гида — тоже.

**Отбраковка фото.** Если из Commons по норвежским POI годится только треть,
галереи будут редкими. Знать это надо на первых 200 снимках, а не перед релизом.
Остаётся открытым.

## Приёмка Этапа 0

Не «готово», а числа: сколько объектов, из них с описанием на `en`, с фото,
средняя длина описания, размер базы в МБ, доля отбраковки по лицензиям.
И явное решение: продолжаем или меняем гипотезу контента.
