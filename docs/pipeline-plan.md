# Пайплайн подготовки данных

Go-часть проекта: превращает открытые источники в `content.sqlite` и пакеты
регионов. Приложение — только витрина; вся тяжёлая работа здесь.

Состояние: написан только `cmd/probe` ([[probe-result]]). Остальное впереди.

## Этапы

```
extract → enrich → media → translate → build
```

| Команда | Что делает | Агент |
|---|---|---|
| `cmd/extract` | OSM `.pbf` → сырые POI, категории, `importance` | `osm-pipeline` |
| `cmd/enrich` | Wikidata, тексты Wikipedia и Wikivoyage | `wiki-enricher` |
| `cmd/media` | Фото с Commons, фильтр лицензий, WebP | `wiki-enricher` |
| `cmd/translate` | Наполнение `translations`, машинный перевод | `l10n-content` |
| `cmd/build` | Сборка SQLite, FTS5, пакеты | `sqlite-schema` |
| `cmd/preview` | Статичные превью карты для топ-1000 | не назначен |

`cmd/preview` появился из [[decisions#Карта вне MVP]] и в §3 спеки отсутствует.

## extract

Потоковое чтение `norway-latest.osm.pbf` через `paulmach/osm` — файл 1.3 ГБ,
целиком в память не грузится.

Требования:
- Маппинг тегов в категории — **одной явной таблицей**, не разбросанными `if`.
- Для way и relation считать центроид, а не первый узел.
- Идентификаторы строго `osm:node/123` / `osm:way/…` / `osm:relation/…`.
- Промежуточный вывод в JSONL с сырыми тегами: переобработка не должна
  требовать повторного чтения `.pbf`.
- Прогон идемпотентный и перезапускаемый с середины.

Отчёт обязателен: количество по категориям и **доля объектов с тегом
`wikidata`** — см. [[#Риски]].

## enrich

Источники разделены по результатам замера ([[probe-result]]):

- **Города → Wikivoyage** (100% покрытия, формат путеводителя)
- **Места → Wikipedia** (90% против 40% у Wikivoyage)
- **Для `no` — только Wikipedia**, норвежского Wikivoyage не существует

Парсеры разные: структура статей не совпадает.

`summary` должен быть самостоятельным текстом на 2–3 предложения, а не
обрезанным началом статьи — офлайн это единственное, что увидит человек
([[data-model#translations]]).

Технически: общий HTTP-клиент с лимитером ~2 rps и дисковым кэшем, ретраи
с учётом `Retry-After`. Сбой запроса **никогда** не трактуется как «статьи нет».

## media

Лицензии проверяются **до** скачивания: только CC0, CC BY, CC BY-SA.
NonCommercial, ND и fair use отбрасываются в лог. Поля `author`, `license`,
`source_url` обязательны.

Отчёт: сколько скачано, сколько отброшено и почему.

## build

Сборка `content.sqlite`, наполнение `search_fts` (включая биграммы для
китайского), `VACUUM`, замер фактического размера против бюджета ~40 МБ.

Затем обязательный прогон `license-auditor` с числами.

## Риски

**Матчинг OSM ↔ Wikidata — узкое место.** Вся схема обогащения держится на
теге `wikidata=Qxxx` в OSM. Если он проставлен у 15% норвежских POI, то 85%
мест останутся без описаний и фото — и хорошее покрытие Wikipedia,
показанное разведкой, не поможет.

Проверяется первым же прогоном `extract` подсчётом по JSONL. Если доля низкая,
нужен нечёткий матчинг по имени и координатам (радиус ~100 м), и его стоимость
надо закладывать сразу, а не обнаруживать на этапе `enrich`.

**Отбраковка фото.** Если из Commons по норвежским POI годится только треть,
галереи будут редкими. Знать это надо на первых 200 снимках, а не перед релизом.

## Приёмка Этапа 0

Не «готово», а числа: сколько объектов, из них с описанием на `en`, с фото,
средняя длина описания, размер базы в МБ, доля отбраковки по лицензиям.
И явное решение: продолжаем или меняем гипотезу контента.
